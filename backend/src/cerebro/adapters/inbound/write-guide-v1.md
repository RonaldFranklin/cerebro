# Cérebro writing guide v1

Save knowledge another session can act on: a decision and its rationale, a configuration, an architectural constraint, a procedure that worked, or a project convention. Skip secrets, transient conversations, raw logs, obvious facts and duplicates.

1. Search with `cerebro_search` before creating. Prefer updating an existing note. Read it in full with `cerebro_read`.
2. Write in English. Send `frontmatter` and a Markdown `body`. Required: a one-line `title` (up to 120 characters), a standalone `summary` (40–300 characters), `area` and `type` (use only the `areas` and `types` returned with this guide), `priority`, and `sensitivity` (public, internal or restricted). Optional: `hub`, `related` (up to 32 ids), `status` (`current`: valid knowledge; `proposed`: planned, not done; `applied`: done, not verified; `verified`: done and tested; `superseded`: replaced; `archived`: history only), `superseded_by` (required when superseded, otherwise omitted), `lang` and `review_by` (`YYYY-MM-DD`).
3. Type fixes priority: `core` is P0 (global rules, 1,500 words across current P0 notes, no `hub`, never restricted), `hub` is P1 (introduces an area, up to 800 words), other types are P2 or P3 (aim for 1,500 words, maximum 3,000) and need `hub`: the id of a note of type `hub`. If the area has none (see `cerebro_overview`), first create it with type `hub`, priority P1; its own `hub` is an optional parent. Hubs need only `write`. Creating, editing, archiving or superseding a core or P0 note needs the `core` scope; on `core_scope_required`, propose the change to the owner.
4. `hub`, `related`, `superseded_by` and body links `[[note-id]]` or `[[note-id#Section]]` must name readable notes at or below this note's sensitivity. Superseded and archived notes count and can be read by id (check `status`). Any `[[note-id]]` is checked, even inside code: in TOML write `[["name"]]`. Titles and summaries cannot contain `[[`.
5. Call `cerebro_write`. For `create`, send a unique `request_id` (1–64 letters, digits, underscores or hyphens). After a lost response, repeat the identical request with that id and token to get the original note id. The service assigns dates and the id (title stem plus a random suffix). Keep titles non-sensitive: filenames and Git history can reveal them, even for restricted notes.
6. For `update`, send the note id as `target` and the full read's `base_hash`, without `request_id`. Replace the whole body (48 KiB UTF-8 at most) and resend all writable frontmatter, including optional fields that are set. Omit `id`, `created` and `updated`. Sensitivity cannot be lowered, and a note cannot move between core, hub and regular types. If `base_hash` is absent, stop. On `stale_base`, read again and reconcile.
7. Fix rejections using their field hints; wait on `rate_limited` (by default 60 write attempts per token per rolling hour).

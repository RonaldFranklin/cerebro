## 2. Admission, suggestions and owner review

Keep ADR-0018's current in-memory validation and NullCurator admission. The first durable row is still a scrubbed rejection or an encrypted, immediately reviewable proposal. With an external provider enabled, atomically attach a job to a newly admitted, eligible revision. Quota denial writes nothing. Policy-blocked submissions, validation rejections and historical rows never enter the paid queue. With provider `null` (default), admission and review work as today. The submitter sees the same bounded receipt. Neither MCP nor browser requests execute model calls.

A separate worker claims one job at a time. Extend the owner-controlled CurateProposal policy for an admitted revision; do not run today's validated-only transition on a needs_owner row. Keep job progress separate from proposal status. A job can publish only against the exact submitted revision and current target base. An owner review, amendment or rejection wins over a late worker. Preserve the original source, validation, timestamp and sealed content. On failure keep the proposal available as needs_owner with a fixed reason, unless the owner has since advanced it. Never rewind an owner action. Old rows remain reviewable and incur no retrospective spend.

| Stage | Inputs and bounded structured result | Next action |
|---|---|---|
| Small model | A minimal eligible proposal projection and capped visible candidate summaries. Accept only an enum for noise, obvious duplicate, continue or uncertain, with a fixed reason code and an optional candidate ID from the supplied list. | Noise/obvious duplicate gives the owner a rejection recommendation; uncertain goes to needs_owner. Neither result deletes a proposal. Only continue can invoke the larger model. |
| Larger model | The proposal, its eligible target and a bounded list of locally selected candidates, all rechecked. Accept exactly one create, merge_into or needs_owner variant. Create/merge carries bounded proposed English text and editable frontmatter. | Build the candidate locally. Reuse schema, field/byte budgets, scanner, duplicate, link, priority and sensitivity validation. Only validated output can be sealed and displayed for approval. Invalid output keeps the original for manual handling. |

Both adapters implement the same narrow JSON Schema subset with closed objects, tagged variants, bounded arrays/strings and exactly one result. Parse strictly (including duplicate keys), validate types, and then construct domain objects. Provider schema enforcement alone cannot authorize a change. The model may suggest English normalization, metadata and visible links. The application assigns identities, timestamps, immutable provenance, base hash and allowed target IDs. Materialize the exact candidate once for inspection. The owner may amend, reject, or explicitly approve through the existing CLI or private UI. Only ApplyProposal commits, with the original Proposed-by, locally determined Curated-by, Approved-by: owner and Proposal-Id.

**Duplicate merging needs an explicit model change.** Today a create cannot take a merge decision, and updates cannot change target. Support a create recommendation to merge into an existing eligible candidate by keeping the original create intact and recording a separate proposed update with the selected target and its inspected hash. Build its diff against that note; approval checks the same hash again. Never retarget an update. A changed or missing target requires fresh owner inspection. For unsupported proposal kinds retain the current owner path. Defer automatic approval and per-agent trust from the roadmap to a future owner decision.

## 3. Disclosure and prompt injection

Enforce ADR-0016 in the application before **either** provider call. Pass adapters a purpose-built wire projection. The existing CurationRequest includes a whole Proposal and cannot safely be serialized. Restrict context to the lower of internal and the recorded submission ceiling. Check the proposed sensitivity, current target, candidate notes, hub, related and superseded IDs, and wikilinks across text fields. Resolve candidate visibility and classification from authoritative content; the index only supplies possible IDs. Exclude hidden identifiers, titles, counts, snippets and references, including those embedded in otherwise visible metadata. Fail closed when the policy cannot establish eligibility. Withhold the entire proposal on a restricted create/change/link or identified restricted excerpt. Existing secret scanning also applies to every outgoing text field. Classification cannot reliably identify unattributed paraphrases of private information; manual classification of source material remains an owner responsibility.

Coordinate each outbound dispatch with content writes so reclassification between selection and send cannot release a stale context. Use the repository's single-writer discipline with a cross-process read/dispatch guard honored by owner edits and apply; verify the snapshot under the guard and hold through transmission, bounded by the call deadline. Reselect after triage. Do not echo raw triage output to the drafting model. Treat proposal, candidate text and model output as untrusted data. Keep system instructions fixed, serialize data separately, and provide no tools, browsing, URL fetching, files, agent credentials or write capabilities. A model-requested command, destination, role, approval flag or extra field has no authority.

The minimum sensitivity of the candidate is the maximum of the proposal's suggested/effective sensitivity and the current merge/update target's sensitivity (use the existing default when absent). Check the floor before storing and again at review/apply against live state. A lower suggestion fails to needs_owner. An increase to restricted is handled locally and cannot be sent back to a provider. Apply the P0/restricted invariant and existing encryption/history warnings. A guessed hidden or absent target yields the same generic fallback. Reject unsafe output without logging or retaining raw provider text.

## 4. Transport, configuration and dependencies

**Recommend direct HTTPS.** The actual distribution and import in the backend lock are `httpx2==2.16.2` (wheel uploaded 2026-11-16), already installed through MCP. Promote this exact pin in the backend manifest and document it under ADR-0013. Expected additional distributions: zero. No new frontend or test dependency is proposed. Verify with a clean locked install and inspect the resolution in PR 5. Two non-streaming JSON endpoints need a small encoder/decoder each. Official SDKs offer generated types, retries and wider API coverage, but would add two dependency trees and still require the same local policy, validation and spending controls. Revisit if the supported wire surface grows.

| Provider | Planned HTTP contract |
|---|---|
| Anthropic | POST to the official Messages endpoint with the provider key, pinned API version, selected model, fixed instructions, bounded output and structured JSON output format. Check stop reason, content shape and usage before accepting a result. [Messages](https://platform.claude.com/docs/en/api/messages/create) · [Structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs) |
| OpenAI | POST to the official Responses endpoint with bearer authentication, selected model, structured text format, output cap and `store: false`. Accept only a completed, expected structured result. Handle refusal and incomplete output explicitly. [Responses](https://platform.openai.com/docs/api-reference/responses/create) · [Structured outputs](https://developers.openai.com/api/docs/guides/structured-outputs) |

Configuration selects one provider per instance, separate exact triage/draft model IDs, model limits and dated USD rates, daily cap, and provider key filename. Require explicit values to enable paid work. Load the key only in the worker from the protected secrets directory, outside both repositories. Use owner-only permissions, regular-file and descriptor-based ownership/symlink checks. Never accept the secret in a prompt, URL, CLI argument or normal configuration. Pin the provider HTTPS origin in the adapter, verify TLS, disable redirect following, environment proxies, SDK/HTTP debug logging and automatic retry. Bound request/response bytes before decoding, disable compressed responses or bound decompression, and enforce a total deadline as well as connect/read/write timeouts. Recommend 30 seconds total for triage and 60 for drafting. Close the client deterministically.

## 5. Budget, metering and recovery

Use one durable per-instance UTC calendar-day ledger across workers and both stages. Recommend a **USD 1.00/day starting cap** when explicitly enabling a paid provider; zero disables all paid calls. Configure exact per-model input/output rates and any enabled billing categories with a source and effective date. Missing prices, unknown billing modes or an unsupported model fail closed. Use integer micro-USD with upward rounding; keep the price snapshot on each reservation. The cap governs the local estimate; the provider invoice remains authoritative.

Before each network dispatch atomically reserve its worst-case cost if it fits the day's remaining balance, including all outstanding holds. Use a documented conservative upper bound for billable input including instructions, framing and schema (fall back to the model's maximum supported input), the enforced output ceiling including reasoning, and the highest applicable configured rate. If no defensible bound fits, return needs_owner without sending. Never estimate from prose length alone. Recheck before the second stage. If only triage fit, record its cost and retain the proposal for the owner. Attribute a call crossing midnight to its reservation day; a restart or backward clock correction cannot reopen a used window.

Persist per-attempt proposal/revision, provider, model, stage, UTC day, token classes, estimated cost, price version and fixed outcome. Aggregate both stages for the owner. Count cached/reasoning tokens according to each provider's inclusive/exclusive totals to avoid double counting. Emit only allowlisted operational fields. For a skipped call record zero calls and zero usage; distinguish unknown usage from zero. On timeout, invalid/missing usage, uncertain delivery or crash after dispatch, retain the full reservation as a conservative charge unless trustworthy usage reconciles it. If valid usage exceeds the bound, record it, suspend that model and flag owner review. Do not retry automatically or switch providers. Use a unique job/revision/stage key and transactionally mark dispatch before network I/O. Recover expired claims without replaying ambiguous calls. Reconcile metering even when another owner action invalidates the result. Never log keys, headers, prompts, note bodies, proposals, raw responses or arbitrary provider errors.

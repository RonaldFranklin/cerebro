# Phase 7 plan — external MCP curator

**Proposed for owner approval.** Cérebro serves a curated work queue to an external agent running under the owner's subscription. The deliverable is a validated recommendation and diff in the private Inbox. The owner decides whether it becomes a commit. This PR changes documentation only. Phase 5 is approved; its manual checkpoint and those of Phases 3 and 4 remain with the owner. ## 2. Credentials and disclosure

- Issue a distinct agent identity for each curator client. Recommend curate-only credentials: reject combining `curate` with other scopes or requesting a restricted ceiling; reject invalid persisted combinations on authentication. Authorize discovery and every call independently. Existing read/propose tokens retain exactly their current tools. A curator receives no generic vault search, owner rights or admission rights. Exclude proposals by the same authenticated agent name, including through a second token. Independently named credentials remain under the owner's control.
- Keep the credential ceiling and accepting socket ceiling independent of request metadata. For each proposal use the minimum of socket, verified token, original admission ceiling and internal. Run the application visibility policy before listing, rendering context and accepting a decision. Use the authoritative notes, not index results, for the target, merge candidates, hubs, related/superseded IDs and wikilinks in text. Omit unsafe supplemental context and withhold the whole proposal if its own payload or required target would disclose hidden content. Treat restricted creations, changes, links and identified restricted quotations as owner-only even on the private listener. Preserve the existing generic policy reason for the owner.
- Return an allowlisted projection, never the raw sealed row, owner preview, validation log, private finding, token or repository path. Filter before counting/paging; opaque page cursors must reveal no skipped IDs, offsets or hidden counts. Hidden, absent and ineligible IDs have identical outward errors. Recheck current classification before sending a coherent response, coordinated with the writer; test a reclassification between listing and reading. A later reclassification cannot retract bytes already delivered. Untagged paraphrases cannot be reliably classified automatically; source sensitivity and owner handling remain necessary.
- Treat proposal text, candidate notes, links and rationales as **data**, including embedded instructions to disclose information, run commands, call other tools or approve a write. Serve only the repository-controlled guide as instructions. The client should use a dedicated session. Server checks must still hold if the client ignores the guide. Future cloud clients need the same credentials, grant and policy; this plan enables no public ingress.

## 3. MCP contract

Proposed names are stable across clients. Use the existing authenticated transports and overall envelope budgets; reject excess bytes before parsing. Close every input object, impose explicit per-field limits, reject unexpected fields, and serialize bounded outputs.

| Tool | Input | Output and limits |
|---|---|---|
| `cerebro_curator_guide` | Empty object | Version, SHA-256 digest and English Markdown from the packaged guide. Same instructions for all clients. Set a 16 KiB UTF-8 release gate. |
| `cerebro_curator_list` | Optional opaque cursor and limit (default 10, max 20) | Eligible proposal IDs, revisions and kinds. Apply all visibility checks to each row. Return a next cursor only when there is another visible row. No proposal bodies or global totals. |
| `cerebro_curator_context` | Proposal ID and inspected revision | Bounded proposal fields, safe validation codes, permitted vocabulary, eligible target, up to five visible related/duplicate candidates, their allowed IDs and relevant excerpts, minimum classification, guide version, and an opaque context_id. Prioritize the full proposed text and required merge base. Mark partial context explicitly; require owner handling when a complete editable base cannot fit. |
| `cerebro_curator_decide` | Proposal ID, revision, context_id, guide version, tagged decision | `create` and `merge_into` require target and a complete English candidate with editable frontmatter and body. `reject` and `needs_owner` require a bounded reason and forbid a candidate. Return only proposal ID, new revision and owner-review receipt. No approval, apply or follow-up access. |

Use existing domain limits for note IDs, lists, title, summary and body, and the stricter of the existing transport envelope and proposed limits (reason 512 UTF-8 bytes, opaque cursor/handle 256 bytes, context 48 KiB serialized). Schema errors use fixed codes with safe field names. Treat proposed links and targets alike whether hidden or nonexistent. Never return unsanitized submitted text in an error. Fix the definitive per-field schema and response-size tests in PRs 3–5.

## 4. Admission, stale work and validation

1. **Admission.** Keep ADR-0018's deterministic validation, NullCurator and atomic token quotas. Every valid proposal stays immediately reviewable by the owner. At admission record a separate pending-curation marker only for eligible new proposals and preserve the submission ceiling. A restricted proposal goes straight to needs_owner without a marker. A scrubbed rejection stays scrubbed. Older rows without trusted eligibility/ceiling remain owner-only. No owner is forced to wait for a client.
2. **Inspection.** Bind a short-lived opaque handle (recommended 15 minutes) to token ID, proposal revision, effective ceiling, guide digest and source IDs, classifications and hashes actually disclosed. Keep provenance local and sealed. Bound active handles and prune expired ones; polling lists does not claim work. A disconnected client leaves the original available. A new inspection after expiry issues a fresh handle.
3. **Decision.** Authenticate again and verify handle binding, guide version, eligibility, provenance and current target/base under the content-write coordination used by apply. Validate note structure, schema, UTF-8 budgets, taxonomy, secret scanner, duplicates, links, sensitivity and domain invariants such as P0 visibility. Derive identity, dates, provenance, approval and hashes locally. The minimum candidate sensitivity is the maximum of the suggested/effective proposal level, current merge target and all disclosed sources. As a conservative default also floor generated text at the curator credential's ceiling: a client can reuse knowledge from another visible context. A dedicated public-ceiling client can recommend public notes when all inputs permit it. Lower suggestions fail. An increase to restricted terminates external access and routes the sealed candidate exclusively to owner review; never echo it. Sanitize/bound reasons and keep them owner-only. Do not persist invalid external payloads.
4. **Targets.** An update can only recommend changing its original target. A create may recommend a merge into a visible existing candidate actually inspected in full. Store that as a separate proposed update against its hash so the original create survives. A create recommendation needs a valid unoccupied target. Preserve existing limits for other kinds; unsupported transformations go to needs_owner. Revalidate source visibility, floor and base at owner review/apply; invalidate a stale recommendation and show the conflict for fresh inspection.
5. **Completion.** Atomically store one sealed recommendation, audit identity and new proposal revision and remove it from the external queue. Competing curators, owner amendments and stale or repeated calls cannot replace the first committed revision. A failed validation leaves the original intact, and the owner can always review it. Return a bounded stale/closed result on a replay with no second write, except that inaccessible IDs always use the common not-found result. `reject` recommends rejection; `needs_owner` ends external inspection. Neither finalizes the owner's decision. Keep the canonical author and derive a valid `curator/…` trailer identity from the authenticated principal, with a collision-free mapping for existing agent names. Only the owner's explicit approve/apply invokes the existing Git path.

## 5. Guide, real clients and acceptance

The guide is released together with the tool schema. It covers organization, English summaries, configured types/areas, priorities, hub membership, safe wikilinks, evidence for merging and criteria for rejection or escalation. PR 5 packages the versioned source at build time; verify byte equality and digest after wheel installation from an unrelated directory. Guide policy never overrides domain validation. [Curator guide](../curator-guide.md)

Follow the [Phase 7 client walkthrough](../agent-integration.md#phase-7-external-curator) after implementation. Use two separately authenticated subscription clients, fresh curator tokens and two synthetic proposals from other identities. Each fetches the guide, inspects one proposal and submits a decision; the owner separately inspects the diff and approves locally. Use a disposable working directory and process-local MCP settings. Keep tokens out of command arguments, prompts, history and global configuration.

The automated gate uses the installed MCP SDK as the external client, with no vendor account or inference network traffic. Seed public, internal, restricted, hidden-link, invalid and legacy proposals. Cover zero restricted bytes across list/context/decision/errors, public-ceiling isolation, direct calls with incorrect scopes, identity substitution, malicious instructions, expired/replayed handles, concurrency and changed source classification. Run all four decisions, verify unchanged content HEAD before owner approval, then compare the approved candidate, parent commit and four trailers. Verify continued operation of the existing five tools and the complete owner-only workflow with no curator connected. Report automated results separately from the subscription-client manual checks.
